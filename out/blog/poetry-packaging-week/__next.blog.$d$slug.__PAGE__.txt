<p><strong>Four videos, one devlog series, one packaging tool: IndyDevDan's diffbro showed that Poetry is the bridge between "it works on my machine" and "pip install diffbro" — and that bridge is the last mile of AI tooling distribution.</strong></p>
<p>Here's what IndyDevDan published between August 2 and August 9, 2026:</p>
<ul><li><strong><a href="https://www.youtube.com/watch?v=5oXh5SvPJ-M">Introducing DIFFBRO</a></strong> — The launch: diffbro, an open-source pip-installable CLI that runs git diffs through ChatGPT for an AI peer review before code reaches a human reviewer. <p>The first three videos are about the code. The fourth is about the <strong>distribution</strong>. And the tool that makes that distribution work is Poetry.</p>
<p>---</p>
<h2 id="the-gap-between-script-and-tool">The Gap Between Script and Tool</h2>
<p>Every developer has a folder of scripts that "would be useful" if other people could run them. The gap between a script and a tool is distribution — and for Python, distribution means <code>pyproject.toml</code>, build, and <code>pypi publish</code>.</p>
<p>Poetry closes that gap in a way that matters for the AI-assisted coding era:</p>
<p><strong>Poetry gives you a single source of truth.</strong> <code>pyproject.toml</code> replaces <code>setup.py</code>, <code>requirements.txt</code>, <code>MANIFEST.in</code>, and <code>setup.cfg</code>. One file. One dependency resolver. One build system. When you're using ChatGPT or Aider to generate your packaging configuration, having a single file to point at reduces the surface area for errors.</p>
<p><strong>Poetry's dependency resolver is strict.</strong> It catches conflicts before they reach users. In the AI coding workflow where you're iterating fast and adding dependencies as you go, having a resolver that tells you *now* that <code>requests>=2.31</code> conflicts with <code>httpx>=0.27</code> saves you from discovering it in a CI pipeline later.</p>
<p><strong>Poetry handles the publish workflow.</strong> <code>poetry build</code> and <code>poetry publish</code> are two commands. The friction is gone. IndyDevDan's walkthrough shows exactly this: write the code, configure Poetry, build, publish. The entire pipeline from working code to <code>pip install</code> is minutes.</p>
<p>---</p>
<h2 id="the-poetry-aider-chatgpt-workflow">The Poetry + Aider + ChatGPT Workflow</h2>
<p>The fourth video in the series is the most practical because it shows a repeatable workflow:</p>
<ol><li><strong>ChatGPT writes the packaging config</strong> — tell it "I need a Poetry-based CLI tool" and it generates the <code>pyproject.toml</code> with the right <code>[tool.poetry.scripts]</code> entry point, dependency declarations, and Python version constraints.</li><li><strong>Aider applies the changes</strong> — the generated config gets written into the project, dependencies are installed, and any structural changes (moving files, adding <code>__init__.py</code>) happen automatically.</li><li><strong>Poetry validates and builds</strong> — <code>poetry build</code> confirms the package structure, resolves dependencies, and produces a distributable artifact.</li><li><strong>Poetry publishes</strong> — <code>poetry publish</code> ships it to PyPI.</li></ol>
<p>The loop is tight. ChatGPT provides the spec, Aider executes the spec, Poetry validates and ships. Each tool handles the part it's best at.</p>
<p>This is the pattern that matters: <strong>AI generates the packaging config, AI modifies the codebase to match the config, and a deterministic tool validates and publishes.</strong> The human is the reviewer, not the typist.</p>
<p>---</p>
<h2 id="what-it-means-for-our-stack">What It Means for Our Stack</h2>
<p>The Edgeless swarm runs on Python scripts. We have dozens of them — cron jobs, pipeline scripts, enrichment tools, API bridges. Most of them have never been packaged.</p>
<p>The diffbro series makes a concrete case for changing that:</p>
<p><strong>1. Every script that's useful to more than one person deserves a <code>pyproject.toml</code>.</strong> Poetry makes this trivial. A <code>pyproject.toml</code> with a <code>[tool.poetry.scripts]</code> entry point turns a script into a CLI that anyone can install with <code>pip install</code>. The overhead is negligible; the distribution gain is enormous.</p>
<p><strong>2. The ChatGPT + Aider + Poetry loop is a packaging template we should codify.</strong> We have a skill for "write a Python script." We should have a skill for "package this script for distribution." The prompt template is: take the script, generate a <code>pyproject.toml</code> with entry point, add <code>click</code> or <code>typer</code> for CLI argument parsing, configure Poetry, build, publish. That's a 30-minute workflow, not a day-long project.</p>
<p><strong>3. Pip-installable CLIs are a better distribution model than MCP servers for internal tools.</strong> MCP is great for tool integration. But for a CLI tool that a developer runs in their terminal, <code>pip install</code> is simpler, more composable, and doesn't require a running server. The diffbro model (CLI with stdin/stdout) is the right default for internal developer tools.</p>

<p>The answer is Poetry. Two commands. Minutes. Done.</p>
