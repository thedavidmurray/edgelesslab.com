<h2 id="why-linear-roadmaps-fail">Why linear roadmaps fail</h2>
<p>Linear roadmaps assume stability. They say "Phase 1 in January, Phase 2 in March." Reality does not care. A dependency moves. A market changes. A teammate gets pulled onto an incident.</p>
<p>When the horizon is short, that is fine. When you are designing systems across months, it is not.</p>
<h2 id="the-reality-mux-loop">The Reality-MUX loop</h2>
<p>Reality-MUX is a planning loop:</p>
<ol><li>Define the current state clearly.</li><li>Define the ideal state with testable outcomes.</li><li>List the smallest set of changes that reduce the distance.</li><li>Execute one slice.</li><li>Recompute the current state.</li></ol>
<p>It is iterative by default. There is no failure state, only a missing cycle.</p>
<h2 id="operational-behavior">Operational behavior</h2>
<ul><li>Small slices reduce risk.</li><li>Explicit current-state definitions prevent drift.</li><li>Completed milestones are durable evidence.</li><li>Definitions of done are public.</li></ul>
<h2 id="why-this-matters-for-shipping">Why this matters for shipping</h2>
<p>Self-evaluating goal loops prevent the comment section pattern: lots of discussion, missing artifacts. If you are not adding files, you are not executing.</p>
<p>The branch between planning and execution is small. The branch between a shipped plan and an academic plan is huge.</p>
<h2 id="the-answer">The answer</h2>
<p>Iterate. Ship. Evaluate. Repeat.</p>b:X
