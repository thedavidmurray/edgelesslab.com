Chapter 01

Why AI Review Differs from Human Review

Understanding the complementary strengths of AI and human reviewers is the foundation of an effective hybrid review process.

Code review has always been a collaborative act — one mind checking another's work. AI-assisted review doesn't replace that collaboration. It redefines the division of labor, freeing human reviewers from mechanical checks so they can focus on judgment, intent, and context that no model can infer from source alone.

To use Claude Code effectively as a reviewer, you need a clear mental model of where it excels, where it falls short, and why those boundaries exist at the architectural level — not just as limitations to work around.

What AI Review Catches Well

🔍

Pattern Recognition at Scale

AI models have internalized millions of code examples. They recognize anti-patterns — God objects, deep nesting, improper exception handling — that human reviewers sometimes miss after hours of context-switching.

🔐

Security Vulnerabilities

OWASP top-10 class issues: SQL injection, XSS, SSRF, insecure deserialization, hardcoded credentials. AI consistently applies security heuristics without fatigue or familiarity bias.

📐

Style & Consistency

Naming convention drift, inconsistent error handling patterns, mixed abstraction levels within a module. AI applies your style guide uniformly across every file in a diff.

📊

Complexity Metrics

Cyclomatic complexity, cognitive complexity, function length, nesting depth. AI quantifies these without the subjectivity that causes "this feels complex" to be ignored in reviews.

📝

Documentation Gaps

Missing docstrings, undocumented parameters, public API without examples, changelog entries. AI catches every gap because it doesn't assume intent from familiarity.

🔄

Dependency Issues

Unused imports, circular dependencies, version constraint mismatches, known-vulnerable packages in lock files. Systematic checks that are tedious to do manually.

What AI Review Misses

These gaps are structural, not incidental. They reflect the fundamental difference between pattern-matching over syntax and understanding human intent.

Critical Limitation

AI cannot determine whether code is correct for your business domain. It can verify that a discount calculation looks syntactically correct. It cannot know that your pricing team decided 15% maximum is a legal requirement in three jurisdictions.

DimensionWhy AI StrugglesHuman Reviewer Advantage
Business LogicNo access to product specs, Jira tickets, Slack threads, or stakeholder decisionsParticipates in planning, understands tradeoffs made
UX IntentCannot run the UI or feel interaction frictionEmpathizes with end-user experience
Team ContextDoesn't know which engineer wrote this or their growth trajectoryCalibrates feedback to the individual
Architectural TradeoffsFlags coupling without knowing if decoupling was a deliberate cost/time decisionWeighs pragmatism vs purity in context
Infra ConstraintsCannot know your database capacity, SLA requirements, or cost ceilingsKnows what "good enough" means for this system
Existing WorkaroundsMay suggest changes that break undocumented behavior relied on elsewhereKnows about the "cursed" coupling in module X

The Complementary Model

The highest-leverage approach treats AI and human review as two sequential gates, not competing alternatives:

workflow
# Optimal review sequence

1. Developer pushes branch
2. AI pre-commit hook → catches style, security, complexity  (2-5 seconds)
3. AI PR review → structured findings report               (15-30 seconds)
4. Human reviewer reads AI report first → skips mechanical  (saves 30-60% time)
5. Human focuses on: business logic, UX, team context
6. Merge only when both gates pass

In practice, teams report that AI review catches 60-80% of comments that would have come from human reviewers, letting humans focus exclusively on the judgment calls that require domain knowledge.

Key Insight

Frame AI review as a first reader, not a gatekeeper. It surfaces issues so human reviewers arrive pre-briefed, not as a replacement for their judgment.

Chapter 02

Setup & Configuration

Getting Claude Code wired into your workflow — from the /review command to custom skills and CLAUDE.md review sections.

Claude Code ships with a powerful review capability out of the box, but the default behavior is generic. This chapter covers the three configuration layers that transform it into a reviewer that knows your stack, your conventions, and your risk tolerance.

Layer 1: The /review Command

The simplest entry point. Claude Code's built-in /review command performs a general-purpose review of staged changes or a specified file.

bash
# Review all staged changes
claude "/review the staged changes for security issues"

# Review a specific file
claude "/review src/auth/middleware.py focusing on injection risks"

# Review a diff from git
git diff HEAD~1 | claude -p "Review this diff for issues"

# Pipe a PR diff for review
gh pr diff 142 | claude -p "Review and output structured findings"

Layer 3: CLAUDE.md Review Section

The CLAUDE.md file is your project's persistent instruction set — it's loaded into context for every Claude Code session. A well-structured review section makes every review context-aware.

markdown — CLAUDE.md (review section)
## Code Review Standards

### Stack
- Python 3.11+, Django 5.x, PostgreSQL 16, Redis 7
- Frontend: React 18, TypeScript 5.x, Tailwind 3.x

### Security Requirements
- ALL database queries MUST use parameterized queries or ORM
- NEVER log PII fields: email, phone, ssn, card_last4
- Authentication: Django auth only — no custom session handling
- File uploads: validate extension AND mime type, max 10MB

- Django models: PascalCase singular (UserProfile, not user_profiles)

- Return structured errors: {"error": "...", "code": "ERR_XXX"}

- New endpoints: require integration test
- New models: require unit test + migration test

Chapter 03

Review Output Format

Structured findings with severity, file, line, and actionable suggestions — a format designed for both human readers and CI systems.

Inconsistent review output is the silent killer of AI review adoption. When findings look different every time — sometimes a paragraph, sometimes bullet points, sometimes nothing at all — reviewers stop trusting the output and revert to ignoring it. Enforcing a structured format solves this.

The Standard Findings Schema

Every finding should carry five fields: severity, location, rule violated, explanation, and suggestion. This structure works in terminals, GitHub PR comments, Slack messages, and databases.

text — finding schema
┌─────────────────────────────────────────────────────────┐
│ CRITICAL  src/auth/login.py:47                           │
├─────────────────────────────────────────────────────────┤
│ Rule:       SQL-INJECTION-001                            │
│ Finding:    String interpolation in raw SQL query.       │
│             User input flows directly into query string. │
│ Suggestion: Use parameterized query:                     │
│             cursor.execute("SELECT * FROM users         │
│               WHERE email = %s", [email])               │
└─────────────────────────────────────────────────────────┘

Prompt Template for Structured Output

This prompt template enforces the schema. Add it to your review skill or use it directly in CI pipelines:

text — review prompt template
Review the following code diff. Output findings in this exact format:

## Summary
- Total findings: X (CRITICAL: X, HIGH: X, MEDIUM: X, LOW: X, INFO: X)
- Overall risk: [LOW|MEDIUM|HIGH|CRITICAL]
- Recommended action: [APPROVE|REQUEST_CHANGES|BLOCK]

## Findings

For each finding:
**[SEVERITY] filename:line**
- Rule: RULE-ID
- Finding: One-sentence description of the issue
- Impact: What could go wrong if this ships
- Suggestion: Exact code fix or refactor guidance
---

Severity scale:
- CRITICAL: Security vulnerability, data loss risk, production outage vector
- HIGH: Logic error, significant performance issue, missing auth check
- MEDIUM: Code smell, maintainability concern, missing test coverage
- LOW: Style violation, naming issue, minor inefficiency
- INFO: Suggestion, refactor opportunity (non-blocking)

Only output findings. Do not summarize the code's purpose.
Do not praise correct code. Do not be verbose in INFO items.

Parsing Findings Programmatically

For CI integration, you'll want to parse this output to set exit codes and post GitHub comments. Here's a lightweight parser:

python — parse_review.py
import re
import sys
from dataclasses import dataclass
from typing import List

SEVERITY_RANK = {"CRITICAL": 5, "HIGH": 4, "MEDIUM": 3, "LOW": 2, "INFO": 1}

@dataclass
class Finding:
    severity: str
    file: str
    line: int
    rule: str
    description: str

def parse_findings(review_output: str) -> List[Finding]:
    findings = []
    pattern = r'\*\*(CRITICAL|HIGH|MEDIUM|LOW|INFO)\s+(.+?):(\d+)\*\*'
    for match in re.finditer(pattern, review_output):
        severity, file_path, line = match.groups()
        findings.append(Finding(
            severity=severity,
            file=file_path,
            line=int(line),
            rule="",
            description=""
        ))
    return findings

def exit_code_for_findings(findings: List[Finding]) -> int:
    """Return non-zero if CRITICAL or HIGH findings exist."""
    max_sev = max((SEVERITY_RANK.get(f.severity, 0) for f in findings), default=0)
    return 1 if max_sev >= SEVERITY_RANK["HIGH"] else 0

if __name__ == "__main__":
    output = sys.stdin.read()
    findings = parse_findings(output)
    print(f"Found {len(findings)} issues")
    sys.exit(exit_code_for_findings(findings))

Pre-Commit Review

Catch issues at the earliest possible moment — before a commit ever reaches the remote.

Pre-commit hooks are the tightest feedback loop in the review pipeline. They run on the developer's machine, in seconds, before any code leaves the local environment. This is where you catch the issues that are cheapest to fix: style violations, obvious security mistakes, missing error handling.

Claude Code hooks use the PreToolUse event system, which fires before tool execution. This gives you the ability to intercept, review, and optionally block commits.

Hook Architecture

json — .claude/hooks/pre-commit-review.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 .claude/hooks/pre-commit-review.py"
          }
        ]
      }
    ]
  }
}
python — .claude/hooks/pre-commit-review.py
#!/usr/bin/env python3
"""Pre-commit review hook — intercepts git commit and runs AI review."""
import json
import subprocess
import sys

def get_staged_diff() -> str:
    result = subprocess.run(
        ["git", "diff", "--cached", "--unified=3"],
        capture_output=True, text=True
    )
    return result.stdout

def run_review(diff: str) -> dict:
    if not diff.strip():
        return {"action": "allow", "findings": []}

    prompt = f"""Review this git diff for CRITICAL and HIGH severity issues only.
Output JSON: {{"action": "block"|"warn"|"allow", "findings": [{{"severity": str, "file": str, "line": int, "issue": str}}]}}
Block only on CRITICAL security issues. Warn on HIGH. Allow on MEDIUM and below.

DIFF:
{diff[:8000]}"""

    result = subprocess.run(
        ["claude", "-p", prompt, "--output-format", "json"],
        capture_output=True, text=True, timeout=30
    )
    try:
        return json.loads(result.stdout)
    except json.JSONDecodeError:
        return {"action": "allow", "findings": []}

def main():
    hook_input = json.loads(sys.stdin.read())
    
    # Only intercept git commit commands
    tool_input = hook_input.get("tool_input", {})
    command = tool_input.get("command", "")
    if "git commit" not in command:
        sys.exit(0)

    diff = get_staged_diff()
    review = run_review(diff)

    if review.get("action") == "block":
        for f in review.get("findings", []):
            print(f"[{f['severity']}] {f['file']}:{f['line']} — {f['issue']}", file=sys.stderr)
        json.dump({"decision": "block", "reason": "CRITICAL security issue found"}, sys.stdout)
        sys.exit(1)

    elif review.get("action") == "warn":
        print("⚠ Review warnings (commit allowed):", file=sys.stderr)
        for f in review.get("findings", []):
            print(f"  [{f['severity']}] {f['file']}:{f['line']} — {f['issue']}", file=sys.stderr)

    sys.exit(0)

if __name__ == "__main__":
    main()
Performance Note

Pre-commit hooks run synchronously. Keep the timeout under 30 seconds or developers will disable them. Use the block only on CRITICAL strategy — be liberal with allows to avoid friction.

Traditional Git Hook Alternative

If you prefer a standard .git/hooks/pre-commit without the Claude Code hook system:

bash — .git/hooks/pre-commit
#!/usr/bin/env bash
set -e

DIFF=$(git diff --cached --unified=3)
if [[ -z "$DIFF" ]]; then exit 0; fi

echo "Running AI pre-commit review..."

RESULT=$(echo "$DIFF" | claude -p "
Review for CRITICAL security issues only. 
Output: PASS or FAIL:reason
" 2>/dev/null)

if [[ "$RESULT" == FAIL* ]]; then
  echo "❌ Pre-commit review failed: ${RESULT#FAIL:}"
  exit 1
fi

echo "✓ Pre-commit review passed"

Chapter 07

Architecture Review

Pattern compliance, coupling analysis, and naming convention enforcement across your codebase.

Architecture review with AI operates at a different level than line-level security or style checks. Here, you're asking Claude to reason about the structure of code — module relationships, abstraction levels, dependency direction — and whether changes preserve or erode architectural integrity.

Pattern Compliance Prompt

text — architecture review prompt
Review this diff for architectural compliance. Our architecture rules:

LAYERING RULES:
- Controllers may call Services and Repositories (never reverse)
- Services may call Repositories and external clients (never call controllers)
- Repositories may only call the database layer (no business logic)
- Models are data classes only (no service calls, no HTTP)

DEPENDENCY RULES:
- Depend on abstractions (interfaces/protocols), not concrete classes
- New dependencies must be injected, not instantiated internally
- No circular imports between modules
- Third-party libraries may only be imported in adapter layers

NAMING RULES:
- Service classes: XxxService (e.g., UserService, PaymentService)
- Repository classes: XxxRepository
- Controller classes: XxxController or XxxView  
- Interface/Protocol: IXxx or XxxProtocol
- DTO classes: XxxRequest, XxxResponse

COUPLING CHECKS:
- Flag any module importing from 3+ other internal modules
- Flag any function with more than 4 parameters (consider DTO)
- Flag any class with more than 10 methods (consider decomposition)
- Flag direct database calls outside Repository layer

Output findings in standard severity format.
CRITICAL = layering violation, HIGH = coupling violation, MEDIUM = naming violation.

Coupling Analysis Script

python — coupling_analysis.py
#!/usr/bin/env python3
"""Analyze import coupling in changed files, then send to Claude for review."""
import ast
import subprocess
import sys
from pathlib import Path
from collections import defaultdict

def get_imports(file_path: str) -> list[str]:
    try:
        tree = ast.parse(Path(file_path).read_text())
    except (SyntaxError, FileNotFoundError):
        return []
    imports = []
    for node in ast.walk(tree):
        if isinstance(node, ast.Import):
            imports.extend(alias.name for alias in node.names)
        elif isinstance(node, ast.ImportFrom):
            if node.module:
                imports.append(node.module)
    return imports

def main():
    changed = subprocess.run(
        ["git", "diff", "--name-only", "HEAD~1"],
        capture_output=True, text=True
    ).stdout.splitlines()

    report = []
    for f in changed:
        if not f.endswith(".py"):
            continue
        imports = get_imports(f)
        internal = [i for i in imports if i.startswith("src.")]
        if len(internal) > 3:
            report.append(f"{f}: HIGH COUPLING — imports {len(internal)} internal modules: {internal}")
    
    if report:
        print("\n".join(report))
    else:
        print("No coupling violations detected")

if __name__ == "__main__":
    main()
Chapter 08

Performance Review

N+1 query detection, memory patterns, and algorithmic complexity analysis.

Performance issues are the most common class of "works correctly but ships wrong" bugs. The code is logically correct, all tests pass, and in development with 10 records it's fine. In production with 10 million records, it costs $40K/month in compute.

Performance Review Prompt

text — .claude/prompts/performance-review.md
Review this code for performance issues. Focus on:

N+1 QUERY DETECTION:
- ORM calls inside loops (most common Django/Rails/ActiveRecord issue)
- Missing select_related() or prefetch_related() in Django
- Missing includes() or eager_load() in Rails
- Missing JOIN or subquery where multiple queries are used

MEMORY PATTERNS:
- Loading entire result sets when pagination or streaming should be used
- Missing .iterator() on large Django querysets  
- Building large lists in memory for aggregation (use DB-side grouping)
- Accumulating objects in module-level collections without cleanup
- Missing generator/lazy evaluation where sequences are consumed once

ALGORITHMIC COMPLEXITY:
- Nested loops over collections (O(n²) or worse) — flag if n could be > 1000
- Linear search in hot paths where dict/set lookup would be O(1)
- Sorting inside loops (should sort once, outside)
- Regex compilation inside loops (compile once, outside)
- String concatenation in loops (use list + join)

IO PATTERNS:
- Synchronous HTTP calls in loops (should batch or async)
- File reads/writes inside loops without buffering
- Missing connection pooling for database/cache clients
- Missing caching for expensive computations called repeatedly

Output format:
CRITICAL = will cause production outage at scale
HIGH = significant regression for >1000 records
MEDIUM = measurable but acceptable in most contexts
LOW = micro-optimization opportunity

        id: review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |

          Verdict: APPROVE, REQUEST_CHANGES, or BLOCK.
          " --dangerously-skip-permissions 2>/dev/null)
          
          echo "REVIEW<> $GITHUB_OUTPUT
          echo "$REVIEW" >> $GITHUB_OUTPUT

Not all AI findings are equal. Add a confidence field to your output format to help human reviewers prioritize which findings to verify:

MEDIUM confidence (60-90%): Likely issue, needs human verification

## Project-Specific Anti-Patterns (Always flag)

### Data Layer
- CRITICAL: Any raw SQL outside of src/db/queries.py
- HIGH: Any direct PostgreSQL connection (must use connection pool at src/db/pool.py)
- HIGH: Any transaction not using our @transactional decorator
- MEDIUM: Any model method that does more than set/get fields

- HIGH: Any thread.start() call (use our thread pool at src/workers/)
- MEDIUM: Missing await on any async function call

Measurement Script

python — review_metrics.py
#!/usr/bin/env python3
"""Calculate AI review quality metrics from GitHub PR data."""
import subprocess
import json
from datetime import datetime, timedelta

def get_pr_comments(days: int = 30) -> list:
    since = (datetime.now() - timedelta(days=days)).isoformat()
    result = subprocess.run([
        "gh", "api", "repos/:owner/:repo/issues/comments",
        "--paginate", "-q",
        f'.[] | select(.created_at > "{since}")'
    ], capture_output=True, text=True)
    return json.loads("[" + result.stdout.replace("\n",",").rstrip(",") + "]")

def calculate_fpr(comments: list) -> float:
    """Estimate FPR from thumbs-down reactions on AI review comments."""
    ai_comments = [c for c in comments if "AI Code Review" in c.get("body","")]
    if not ai_comments:
        return 0.0
    # Count comments with negative reactions as false positives
    fp = sum(1 for c in ai_comments if c.get("reactions",{}).get("-1",0) > 0)
    return fp / len(ai_comments)

def print_dashboard(days: int = 30):
    comments = get_pr_comments(days)
    ai_comments = [c for c in comments if "AI Code Review" in c.get("body","")]
    fpr = calculate_fpr(comments)
    
    print(f"=== AI Review Quality Dashboard ({days}d) ===")
    print(f"Total AI reviews:     {len(ai_comments)}")
    print(f"False positive rate:  {fpr:.1%}")
    print(f"Status: {'GOOD' if fpr < 0.15 else 'NEEDS TUNING'}")

if __name__ == "__main__":
    print_dashboard()
