What Agents Actually Are

Stripped of the marketing, an agent is a model in a loop with access to tools. That's it. Everything else is implementation detail.

The honest definition

An agent is a language model that runs in a loop, calling tools and receiving their results, until it decides it's done. The loop is the critical part — a single LLM call that outputs text is not an agent. An LLM call that reads a file, decides what to do next, writes a file, and checks the result is an agent.

The reason this matters: the failure modes of single calls and agents are completely different. A single call can hallucinate. An agent can hallucinate, get stuck in loops, accumulate context debt, call tools in the wrong order, and run indefinitely at real cost.

The three things that define an agent

1. A loop. The model runs multiple times, not once. Each iteration can use the outputs of previous iterations. This is what enables reasoning over multiple steps.

2. Tools. The model can take actions that affect the world: read files, write files, call APIs, run code, spawn other agents. Without tools, it's just a chatbot.

3. A stopping condition. The loop terminates when the model decides it's done, when a condition is met, or when a timeout fires. Without a stopping condition, you have an infinite loop.

┌─────────────────────────────────────┐ │ AGENT LOOP │ │ │ │ Input / Context │ │ ↓ │ │ ┌─────────┐ tool call │ │ │ Model │ ─────────────→ Tool │ │ └─────────┘ │ │ │ ↑ │ │ │ └──── tool result ──────┘ │ │ │ │ Loop until: done | error | timeout │ └─────────────────────────────────────┘

What agents are not

Not magic. An agent is bounded by the model's capabilities on each individual call. Chaining weak reasoning in a loop produces weak results at higher cost. The loop amplifies, not compensates.

Not autonomous. "Autonomous" implies the agent understands goals the way humans do. It doesn't. It pattern-matches on the instructions and context you give it. Give it bad context, get bad outputs — reliably, at scale.

Not reliable by default. Reliability is engineered: explicit error handling, output validation, retry limits, checkpoints, structured logging. These don't come for free.

The agentic spectrum

FormLoopToolsWhen it makes sense
Single callNoNoClassification, summarization, generation
Single call + toolsNoYesLookup, fetch, one-shot transformation
ReAct agentYesYesMulti-step tasks with unknown path
Multi-agentYes (nested)YesParallel work, validation, specialization
When to use this mental model

Before building anything, ask: does this require a loop? If a single LLM call with the right tools can solve the problem, use that. The loop is what creates complexity — justify it explicitly.

Common mistakes
  • Building agents for simple tasks. If you know all the steps upfront, write a script. Agents are for tasks where the path isn't known until execution.
  • No stopping condition. Always define when an agent is done before you build it. "Runs until done" is not a stopping condition.
  • Ignoring cost. An agent that runs 20 iterations at $0.01 per call costs $0.20 per execution. At scale, this matters. Measure before you deploy.

The Claude Code Agent Model

Claude Code has a specific model for how agents work: subagents, tools, permissions, and CLAUDE.md context. Understanding this model is prerequisite to using it well.

How Claude Code runs agents

Claude Code exposes the Task tool, which spawns a subagent: a new Claude instance with its own context window, running in a sandboxed environment. The parent agent can pass a prompt and receive back the result when the subagent completes.

The key constraint: subagents do not share context with their parent. Each subagent starts fresh with only what you explicitly give it in the prompt. This is a feature, not a bug — it enforces clean interfaces between agent stages.

Subagent types

Scheduled agentCron / external triggerStarts fresh from CLAUDE.mdRecurring jobs, monitoring
Piped agentCLI: claude -p "..."Prompt onlyScripted pipelines, CI

The tool surface

Every Claude Code agent has access to the same core tools. Understanding which tools are available — and which are expensive — shapes how you design agents.

CLAUDE.md: the agent's constitution

Every agent session loads CLAUDE.md from the working directory and parent directories. This file is the primary mechanism for encoding persistent agent behavior — conventions, prohibited patterns, canonical paths, tool usage rules.

Think of CLAUDE.md as a system prompt that survives across sessions. Whatever you want every agent to know without being told, put it there.

CLAUDE.md — minimal agent constitutionmarkdown
# Agent Constitution

## Canonical Paths
- Output: `/output/` only
- Logs: `/logs/YYYY-MM-DD.log`
- Never write to project root

## Error Handling
- Wrap all Bash calls in try/except equivalents
- On failure: log the error, do not retry more than 3 times
- Always report failures explicitly — never silently continue

## Prohibited Actions
- Never delete files without explicit instruction
- Never commit to git without verification step
- Never call external APIs with user data without sanitization

## Tool Preferences
- Read/Glob/Grep over Bash for file operations
- Edit over Write for existing files
- Report tool errors immediately, do not swallow them

Permissions model

Claude Code uses an allowlist permission model. In non-interactive mode (--dangerously-skip-permissions), all tool calls are permitted without confirmation — this is the mode used in pipelines and cron jobs. In interactive mode, destructive actions prompt the user.

Permission design rule

Design agents to work correctly with the minimum permission set. If an agent only needs to read files and call one API, it shouldn't need Bash access. Minimize the blast radius of a misbehaving agent by constraining its tools at the CLAUDE.md level.

The skill.md pattern

Complex behaviors are encoded in skill files — markdown documents that an agent reads at the start of a task to load specialized knowledge. This is how you give an agent domain expertise without burning tokens on every session.

.claude/skills/code-reviewer/skill.mdmarkdown
# Code Review Skill

Load this skill when asked to review code.

## Review Protocol
1. Read all changed files before commenting on any
2. Check: correctness, error handling, tests, naming
3. Output structured report: CRITICAL / WARNING / SUGGESTION
4. Never suggest rewrites without explaining the bug being fixed

## Output Format
```
REVIEW SUMMARY
Files: N
Critical issues: N
Warnings: N

CRITICAL
[file:line] description — why this is a problem

WARNING
[file:line] description

SUGGESTION
[file:line] description (optional, skip if none)
```

## What NOT to flag
- Style preferences without a concrete impact
- Things that work correctly even if you'd write them differently
- Missing features not in scope of the PR
Common mistakes
  • Assuming context carries across subagents. It doesn't. Always pass everything a subagent needs explicitly in its prompt.
  • Putting logic in CLAUDE.md that belongs in a skill. CLAUDE.md loads every session. Keep it to universal constraints. Domain knowledge goes in skills loaded on demand.
  • Spawning subagents for tasks that don't need isolation. The Task tool costs tokens. For sequential steps in the same context, just do them sequentially.

Agents vs Direct Tool Calls

The most common mistake in agent design is using an agent when a direct tool call would work. More moving parts = more failure modes. Add complexity only when it earns its keep.

The decision tree

Before reaching for an agent, answer these questions in order:

  1. Do I know all the steps upfront? If yes, write a script. Scripts are deterministic, testable, and cheap.
  2. Can a single LLM call with the right context solve it? If yes, use a single call. Add retrieval or tool calls as needed, but stay in one turn.
  3. Does the task require dynamic decision-making across multiple steps? If yes, consider an agent.
  4. Does the task benefit from parallel execution or independent validation? If yes, consider multi-agent.

When a direct call wins

A direct call (single LLM invocation, possibly with tools) is preferable when:

  • The input-output transformation is defined: summarize this, classify that, extract these fields
  • You can write the full prompt in advance with all needed context
  • The result is self-contained — no need to check external state mid-task
  • Latency matters and you can't afford multiple round-trips

import anthropic

{codebase_context}

Bug report:
{bug_report}

Reply with only the severity label and one sentence justification.
"""
        }]
    )
    return response.content[0].text

When an agent wins

An agent earns its complexity when:

  • The task requires exploring unknown territory — you don't know which files are relevant until you start reading
  • The task requires dynamic decision-making — step N's action depends on step N-1's result
  • The task requires external state checks — run tests, check if a service is up, verify a file was written
  • The task benefits from self-correction — detect an error, adjust, retry

# Good: unknown path, multi-step, self-correcting

1. Read the file to understand the usage
2. Determine if it can be safely migrated
3. Perform the migration if safe
4. Run the tests for that module

The cost of getting it wrong

Wrong choiceConsequence
Agent when script would work10-50x cost, unpredictable behavior, harder to test
Script when agent neededBrittle hardcoding, breaks on edge cases, manual intervention required
Single agent when multi-agent neededContext overflow, conflation of separate concerns, no validation
Multi-agent when single agent sufficesCoordination overhead, harder debugging, unnecessary latency
Heuristic that works in practice

If you can fully specify the task in a bullet list before running it, use a script or single call. If you find yourself writing "and then depending on what you find..." — that's agent territory.

Common mistakes
  • Wrapping every LLM call in an agent framework. Framework overhead adds latency and cost. Use a framework when you need orchestration, not as default.
  • Building agents for one-shot tasks. If the task only runs once and the path is clear, write the script. Agents are for tasks you'll run repeatedly with variable inputs.
  • Not benchmarking the simple approach first. Build the dumb version, measure it, then decide if agents improve it enough to justify the complexity.

Agent Communication Patterns

How agents pass information to each other determines system reliability. Clean interfaces between agents are what make multi-agent systems debuggable.

The four communication channels

ChannelMechanismProsCons
Prompt injectionPass data in the subagent promptSimple, explicitToken cost, size limits
FilesystemAgent A writes file, Agent B reads itDurable, inspectableRequires agreed schema
Structured outputAgent returns JSON/YAML parsed by parentTyped, parseableModel must reliably emit format
External storeDatabase, queue, key-value storeDecoupled, persistentOperational overhead

Prompt injection

The simplest channel: serialize what Agent A knows and include it in Agent B's prompt. Works well for moderate amounts of structured data.

Passing structured data via promptpython
import json
from anthropic import Anthropic

client = Anthropic()

def run_subagent(task: str, context: dict) -> str:
    context_str = json.dumps(context, indent=2)
    prompt = f"""You are a specialized agent. Here is your context:

{context_str}

Your task:
{task}

Complete the task and report results in JSON format with keys:
- success (bool)
- result (any)
- errors (list of strings, empty if none)
"""
    
    response = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=4096,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.content[0].text

Filesystem as message bus

For larger payloads or when durability matters, write to an agreed file location. Each agent reads what it needs, writes what it produces. This naturally creates an audit trail.

Filesystem handoff protocolmarkdown
# In CLAUDE.md or skill file

## Inter-Agent Handoff Protocol

All agents write their output to: `/tmp/agent-pipeline/{run_id}/{stage}.json`

Output schema (all stages must comply):
```json
{
  "stage": "string",
  "agent": "string",
  "timestamp": "ISO-8601",
  "success": true,
  "result": {},
  "errors": [],
  "metadata": {}
}
```

Next agent reads previous stage output before starting.
On error: write success=false, populate errors[], halt.

Structured output contracts

When a parent agent needs to parse a subagent's output, enforce a schema. Use tool_use or require JSON in the prompt — never try to parse free-form text between agents.

Enforcing structured output with tool_usepython
analysis_tool = {
    "name": "report_analysis",
    "description": "Report analysis results in structured format",
    "input_schema": {
        "type": "object",
        "properties": {
            "issues_found": {"type": "integer"},
            "severity": {"type": "string", "enum": ["critical", "high", "medium", "low"]},
            "summary": {"type": "string"},
            "recommendations": {"type": "array", "items": {"type": "string"}}
        },
        "required": ["issues_found", "severity", "summary"]
    }
}

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=2048,
    tools=[analysis_tool],
    tool_choice={"type": "tool", "name": "report_analysis"},
    messages=[{"role": "user", "content": prompt}]
)

# Guaranteed structured output — no parsing needed
result = response.content[0].input
Design principle

Treat inter-agent communication like an API contract. Define the schema before you build either agent. If you can't describe what Agent A passes to Agent B in a JSON schema, the design isn't ready.

Common mistakes
  • Parsing free-form text between agents. Regex on LLM output is fragile. Use tool_use or explicitly request JSON with a defined schema.
  • Passing entire codebases through prompt injection. There are token limits. Use filesystem or retrieval for large payloads.
  • No shared error schema. When a subagent fails, the parent needs to know in a structured way. Define error reporting format upfront.

The Builder-Validator Pattern

Separate the agent that builds from the agent that validates. The builder is optimistic. The validator is adversarial. Neither knows what the other will do.

The problem it solves

A single agent that builds and validates its own work has a conflict of interest. It tends to validate what it built, not what the requirements say. Separating the roles forces honest evaluation.

BUILDER AGENT VALIDATOR AGENT ───────────────── ─────────────────── Receives: spec Receives: spec + output Goal: produce output Goal: find failures Bias: "I built this well" Bias: "Does this meet spec?" │ │ └──── artifact ────────────────┘ │ pass / fail + reasons

Implementation

builder_validator.pypython
import anthropic
import json

client = anthropic.Anthropic()

def builder_agent(spec: str, context: dict = {}) -> str:
    """Produces an artifact from a spec. Optimistic builder."""
    prompt = f"""You are a builder. Produce a complete implementation of this spec.

SPEC:
{spec}

CONTEXT:
{json.dumps(context, indent=2)}

Produce the implementation. Do not add validation logic — that's handled separately.
Focus on correctness and completeness."""

    response = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=8192,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.content[0].text

def validator_agent(spec: str, artifact: str) -> dict:
    """Validates an artifact against a spec. Adversarial validator."""
    prompt = f"""You are a validator. Your job is to find failures.

ORIGINAL SPEC:
{spec}

ARTIFACT TO VALIDATE:
{artifact}

Be thorough and adversarial. Check:
1. Does it fulfill every requirement in the spec?
2. Are there edge cases not handled?
3. Are there errors or bugs?
4. Is anything missing?

Respond in JSON:
{{
  "passed": false,
  "score": 0-100,
  "failures": ["list of specific failures"],
  "warnings": ["non-blocking issues"],
  "verdict": "one sentence summary"
}}"""

    response = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt}]
    )
    
    text = response.content[0].text
    # Extract JSON from response
    start = text.find('{')
    end = text.rfind('}') + 1
    return json.loads(text[start:end])

def build_and_validate(spec: str, max_iterations: int = 3) -> dict:
    """Full build-validate loop with automatic retry on failure."""
    history = []
    
    for iteration in range(max_iterations):
        # Include previous failures in builder context
        context = {"iteration": iteration, "previous_failures": history}
        
        artifact = builder_agent(spec, context)
        validation = validator_agent(spec, artifact)
        
        history.append({
            "iteration": iteration,
            "score": validation["score"],
            "failures": validation["failures"]
        })
        
        if validation["passed"]:
            return {
                "success": True,
                "artifact": artifact,
                "iterations": iteration + 1,
                "final_score": validation["score"]
            }
    
    return {
        "success": False,
        "artifact": artifact,
        "iterations": max_iterations,
        "history": history
    }

Skill file variant

.claude/skills/builder-validator/skill.mdmarkdown
## Builder-Validator Activation

When building something that will be evaluated:
1. First, complete the full implementation
2. Then, switch perspective: "I am now a validator who did not build this"
3. Apply the validation checklist without mercy
4. If failures found: rebuild with failures in context, validate again
5. Maximum 3 iterations before escalating to human review

## Validator Checklist
- [ ] Every requirement in the spec is satisfied
- [ ] Edge cases are handled (empty input, null, overflow)
- [ ] Errors are caught and reported, not silently swallowed
- [ ] The output format matches what was specified
- [ ] No assumptions were made that aren't in the spec
When to use this

Code generation, document writing, configuration generation, data transformation — any task where you can define a spec upfront and check the output against it. Especially valuable when the output will be deployed or sent to users.

Common mistakes
  • Using the same model for both roles. Works, but give each a different system prompt that emphasizes their distinct goal. The builder should not be defensive; the validator should not be lenient.
  • No iteration limit. Always set a max. If the build-validate loop hasn't converged in 3-4 iterations, the spec is probably ambiguous — human review is needed.
  • Vague validation criteria. "Is it good?" is not a validation spec. Define exactly what pass means before running the builder.

Fan-out / Fan-in

Decompose a large task into parallel subtasks, run them simultaneously, then aggregate the results. Trading sequential latency for parallel throughput.

The problem it solves

Some tasks are embarrassingly parallel: analyzing 50 files, researching 10 topics, processing 100 records. Running them sequentially is slow and wastes the parallelism available. Fan-out runs them simultaneously and fan-in combines the results.

INPUT │ ┌───────┴───────┐ split into N subtasks │ │ │ ↓ ↓ ↓ Agent-1 Agent-2 Agent-3 ← parallel execution │ │ │ └───────┴───────┘ │ aggregate │ OUTPUT

Implementation with asyncio

fan_out.pypython
import asyncio
import anthropic
from typing import TypedDict

client = anthropic.AsyncAnthropic()

class SubtaskResult(TypedDict):
    subtask_id: str
    success: bool
    result: str
    error: str | None

async def run_subtask(subtask_id: str, task: str, context: str) -> SubtaskResult:
    """Run a single subtask. Returns structured result even on failure."""
    try:
        response = await client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=[{
                "role": "user",
                "content": f"""Subtask ID: {subtask_id}

Context: {context}

Task: {task}

Complete this specific subtask. Be thorough but focused only on this task."""
            }]
        )
        return SubtaskResult(
            subtask_id=subtask_id,
            success=True,
            result=response.content[0].text,
            error=None
        )
    except Exception as e:
        return SubtaskResult(
            subtask_id=subtask_id,
            success=False,
            result="",
            error=str(e)
        )

async def fan_out(subtasks: list[dict]) -> list[SubtaskResult]:
    """Run all subtasks in parallel, return all results."""
    coros = [
        run_subtask(s["id"], s["task"], s["context"])
        for s in subtasks
    ]
    return await asyncio.gather(*coros)

def fan_in(results: list[SubtaskResult], aggregation_prompt: str) -> str:
    """Synchronous aggregation step after fan-out completes."""
    # Separate successes from failures
    successes = [r for r in results if r["success"]]
    failures = [r for r in results if not r["success"]]
    
    results_text = "\n\n".join([
        f"=== {r['subtask_id']} ===\n{r['result']}"
        for r in successes
    ])
    
    failures_text = "\n".join([
        f"- {r['subtask_id']}: {r['error']}"
        for r in failures
    ])
    
    client_sync = anthropic.Anthropic()
    response = client_sync.messages.create(
        model="claude-opus-4-5",  # Upgrade for aggregation
        max_tokens=8192,
        messages=[{
            "role": "user",
            "content": f"""{aggregation_prompt}

SUBTASK RESULTS ({len(successes)} succeeded, {len(failures)} failed):

{results_text}

{"FAILED SUBTASKS:" + chr(10) + failures_text if failures else ""}

Synthesize a complete, coherent response from these results."""
        }]
    )
    return response.content[0].text

# Usage example
async def analyze_codebase(files: list[str]) -> str:
    subtasks = [
        {"id": f, "task": "Analyze this file for security vulnerabilities", "context": f}
        for f in files
    ]
    results = await fan_out(subtasks)
    return fan_in(results, "Produce a security audit report from these file analyses.")

Rate limit management

Fan-out hits rate limits fast. Use a semaphore to cap concurrency:

Rate-limited fan-outpython
CONCURRENCY_LIMIT = 5  # Anthropic tier-dependent
semaphore = asyncio.Semaphore(CONCURRENCY_LIMIT)

async def run_subtask_limited(subtask_id: str, task: str, context: str):
    async with semaphore:
        return await run_subtask(subtask_id, task, context)
When to use this

Batch processing (files, records, URLs), parallel research across independent topics, multi-language translation, multi-model ensemble (run same task on different models, aggregate). Any task where N subtasks don't depend on each other's results.

Common mistakes
  • Ignoring partial failures. If 3 of 10 subtasks fail, the fan-in still needs to know. Never discard failure information — include it in the aggregation.
  • Using expensive models for all subtasks. Fan-out multiplies cost by N. Use claude-haiku for individual subtasks and claude-opus only for aggregation.
  • No concurrency limit. Unbounded parallel requests will hit rate limits and fail. Always use a semaphore.

Pipeline Pattern

A sequential chain where each stage transforms the output of the previous one. Predictable, inspectable, and easy to debug — the right default for most multi-agent work.

The problem it solves

When a task has a well-defined sequence of transformations — each depending on the last — a pipeline encodes that sequence explicitly. Each stage has a single responsibility. Failures are easy to locate: the pipeline stopped at stage N.

Input │ ↓ Stage 1: Fetch + Parse │ ↓ Stage 2: Analyze │ ↓ Stage 3: Generate │ ↓ Stage 4: Validate │ ↓ Output

Implementation

pipeline.pypython
from dataclasses import dataclass, field
from typing import Callable, Any
import anthropic
import time

@dataclass
class PipelineStage:
    name: str
    prompt_template: str  # Use {input} and {context} placeholders
    model: str = "claude-sonnet-4-5"
    max_tokens: int = 4096
    transform: Callable | None = None  # Optional post-processing

@dataclass
class PipelineResult:
    success: bool
    output: Any
    stages_completed: list[str] = field(default_factory=list)
    failed_at: str | None = None
    error: str | None = None
    stage_outputs: dict = field(default_factory=dict)

class Pipeline:
    def __init__(self, stages: list[PipelineStage], context: dict = {}):
        self.stages = stages
        self.context = context
        self.client = anthropic.Anthropic()

    def run(self, initial_input: str) -> PipelineResult:
        current_input = initial_input
        stage_outputs = {}
        
        for stage in self.stages:
            try:
                prompt = stage.prompt_template.format(
                    input=current_input,
                    context=self.context,
                    **stage_outputs  # Previous stage outputs available
                )
                
                response = self.client.messages.create(
                    model=stage.model,
                    max_tokens=stage.max_tokens,
                    messages=[{"role": "user", "content": prompt}]
                )
                
                output = response.content[0].text
                if stage.transform:
                    output = stage.transform(output)
                
                stage_outputs[stage.name] = output
                current_input = output
                
            except Exception as e:
                return PipelineResult(
                    success=False,
                    output=None,
                    stages_completed=list(stage_outputs.keys()),
                    failed_at=stage.name,
                    error=str(e),
                    stage_outputs=stage_outputs
                )
        
        return PipelineResult(
            success=True,
            output=current_input,
            stages_completed=list(stage_outputs.keys()),
            stage_outputs=stage_outputs
        )

# Example: code migration pipeline
migration_pipeline = Pipeline(stages=[
    PipelineStage(
        name="parse",
        model="claude-haiku-4-5",  # Fast, cheap for parsing
        prompt_template="""Parse this code and identify all patterns that need migration.
Output a JSON list of: {{"pattern": "...", "location": "...", "reason": "..."}}

Code:
{input}"""
    ),
    PipelineStage(
        name="migrate",
        model="claude-sonnet-4-5",  # Better reasoning for transformation
        prompt_template="""Migrate this code. Patterns to migrate: {parse}

Original code:
{input}

Apply all migrations. Output the complete migrated code."""
    ),
    PipelineStage(
        name="validate",
        model="claude-sonnet-4-5",
        prompt_template="""Validate this migrated code.
Original patterns identified: {parse}
Migrated code: {input}

Confirm all patterns were migrated. List any remaining issues."""
    ),
])
When to use this

Data transformation chains, content processing (fetch → extract → summarize → format), code migration, document generation. Whenever you can draw a clear linear flow before implementation.

Optimization tip

Use cheaper models for early pipeline stages (parsing, extraction) and reserve expensive models for generation and reasoning stages. A 5-stage pipeline with claude-haiku on stages 1-2 can cut costs by 60% with no quality loss.

Common mistakes
  • No intermediate state persistence. Always save stage_outputs. When a pipeline fails at stage 4, you don't want to rerun stages 1-3.
  • Monolithic prompts. If a pipeline stage's prompt is doing multiple things, split it into two stages. Each stage should have exactly one job.
  • Silent stage failures. If stage 2 produces garbage, stage 3 will silently process garbage. Validate stage outputs before passing them forward.

The Ralph Wiggum Loop

Iterative self-improvement: the agent produces output, evaluates it, and improves it until a quality threshold is met. Named for the character who keeps trying regardless of results.

The problem it solves

First drafts are rarely final drafts. A single generation pass optimizes for completing the task, not for quality. The Ralph Wiggum loop explicitly separates generation from critique, giving the model permission to find fault with its own work.

Input │ ↓ Generate ←──────────────┐ │ │ ↓ │ Critique revision │ │ ↓ │ Score ≥ threshold? ─No──┘ │ Yes ↓ Output

Implementation

import anthropic
import json
from dataclasses import dataclass

client = anthropic.Anthropic()

@dataclass
class LoopConfig:
    quality_threshold: int = 85   # Score 0-100
    max_iterations: int = 4
    generation_model: str = "claude-sonnet-4-5"
    critique_model: str = "claude-sonnet-4-5"

def generate(task: str, previous_drafts: list[dict], model: str) -> str:
    history = ""
    if previous_drafts:
        history = "\n\n".join([
            f"DRAFT {d['iteration']+1} (score: {d['score']}):\n{d['draft']}\n\nCRITIQUE:\n{d['critique']}"
            for d in previous_drafts
        ])
    
    prompt = f"""Task: {task}

{"Previous attempts and critiques:" + chr(10) + history if history else "This is your first attempt."}

Produce {"an improved version" if history else "your best version"} now.
{"Address every critique from the previous attempt." if history else ""}"""
    
    response = client.messages.create(
        model=model, max_tokens=8192,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.content[0].text

def critique(task: str, draft: str, criteria: list[str], model: str) -> dict:
    criteria_str = "\n".join([f"- {c}" for c in criteria])
    prompt = f"""You are an expert critic. Be honest and demanding.

Task: {task}

Evaluation criteria:
{criteria_str}

Draft to evaluate:
{draft}

Score this draft 0-100 and explain what's missing or wrong.
Respond in JSON:
{{
  "score": 75,
  "passed": false,
  "strengths": ["..."],
  "weaknesses": ["specific, actionable critique"],
  "improvement_instructions": "Concrete instructions for the next draft"
}}"""
    
    response = client.messages.create(
        model=model, max_tokens=2048,
        messages=[{"role": "user", "content": prompt}]
    )
    text = response.content[0].text
    start, end = text.find('{'), text.rfind('}') + 1
    result = json.loads(text[start:end])
    result["passed"] = result["score"] >= 85
    return result

def improvement_loop(task: str, config: LoopConfig = None) -> dict:
    config = config or LoopConfig()
    criteria = config.criteria or [
        "Completeness: addresses all aspects of the task",
        "Accuracy: factually correct, no errors",
        "Clarity: well-structured, easy to follow",
        "Quality: professional, polished output"
    ]
    
    history = []
    for iteration in range(config.max_iterations):
        draft = generate(task, history, config.generation_model)
        evaluation = critique(task, draft, criteria, config.critique_model)
        
        history.append({
            "iteration": iteration,
            "draft": draft,
            "score": evaluation["score"],
            "critique": evaluation["improvement_instructions"]
        })
        
        if evaluation["passed"]:
            return {"success": True, "output": draft, "score": evaluation["score"],
                    "iterations": iteration + 1, "history": history}
    
    best = max(history, key=lambda x: x["score"])
    return {"success": False, "output": best["draft"], "score": best["score"],
            "iterations": config.max_iterations, "history": history}
When to use this

Writing tasks (documentation, reports, summaries), code generation with quality requirements, configuration generation, any task where "good enough on first try" isn't acceptable and you can define quality criteria.

Common mistakes
  • Vague criteria. "High quality" is not a criterion. "Addresses all five requirements from the spec" is. The critique is only as good as the criteria you give it.
  • No convergence check. Sometimes the model improves from 70 to 72 to 71 — oscillating, not improving. Track score history and stop if improvement stalls.
  • Too many iterations with expensive models. Use haiku for generation, sonnet for critique. Or set the threshold lower and accept a 75-score output over 4 expensive iterations.

Supervisor Pattern

An orchestrator agent breaks down a complex task, delegates subtasks to specialized worker agents, and synthesizes the results. Separation of planning from execution.

The problem it solves

Complex tasks require both high-level planning (what needs to be done?) and domain-specific execution (how to do each part?). Mixing these in one agent bloats the context and creates conflated concerns. The supervisor handles planning; workers handle execution.

SUPERVISOR (planning) / | \ ↓ ↓ ↓ Worker-1 Worker-2 Worker-3 (code) (docs) (tests) \ | / ↓ ↓ ↓ SUPERVISOR (synthesis)

def supervisor_synthesize(goal: str, subtask_results: list[dict]) -> str:
    """Supervisor synthesizes worker results into final output."""
    results_text = "\n\n".join([
        f"=== {r['subtask_id']} ({r['worker']}) ===\n{r['result']}"
        for r in subtask_results if r["success"]
    ])
    
    response = client.messages.create(
        model="claude-opus-4-5",
        max_tokens=8192,
        messages=[{"role": "user", "content": f"""Synthesize these worker results into a coherent final output.

Original goal: {goal}

Worker results:
{results_text}

Produce the final, integrated output that fulfills the original goal."""}]
    )
    return response.content[0].text

class SupervisorSystem:
    def __init__(self, workers: dict[str, WorkerFn]):
        """workers: {"worker-name": callable(instruction, context) -> str}"""
        self.workers = workers

    def run(self, goal: str) -> dict:
        # Plan
        subtasks = supervisor_plan(goal, list(self.workers.keys()))
        
        # Execute (respects depends_on ordering)
        completed = {}
        results = []
        
        for subtask in subtasks:
            # Build context from dependencies
            dep_context = {d: completed.get(d, "(not available)") for d in subtask["depends_on"]}
            
            worker_fn = self.workers.get(subtask["worker"])
            if not worker_fn:
                results.append({"subtask_id": subtask["id"], "worker": subtask["worker"],
                                 "success": False, "result": f"Unknown worker: {subtask['worker']}"})
                continue
            
            try:
                result = worker_fn(subtask["instruction"], dep_context)
                completed[subtask["id"]] = result
                results.append({"subtask_id": subtask["id"], "worker": subtask["worker"],
                                 "success": True, "result": result})
            except Exception as e:
                results.append({"subtask_id": subtask["id"], "worker": subtask["worker"],
                                 "success": False, "result": str(e)})
        
        # Synthesize
        final = supervisor_synthesize(goal, results)
        return {"success": True, "output": final, "subtasks_run": len(results), "details": results}
When to use this

Complex multi-domain tasks: feature implementation (code + tests + docs), research synthesis (search + analyze + write), deployment (build + test + deploy + verify). Use when different subtasks need fundamentally different expertise or tools.

Common mistakes
  • Using opus for all workers. The supervisor needs the best model for planning. Workers often don't. Downgrade worker models to cut costs.
  • No dependency resolution. If subtask 3 depends on subtask 1, execute in order. Parallel workers that share state will conflict.
  • Supervisor that does work. If the supervisor is executing code or writing files, it's doing worker work. Keep the supervisor in planning/synthesis mode only.

Consensus Pattern

Multiple independent agents vote on a decision. Useful when confidence in any single agent's judgment is insufficient. Reduces variance at the cost of multiplied token spend.

The problem it solves

Some decisions are high-stakes enough that a single model's opinion isn't trustworthy. Running the same question through N independent agents and taking the majority answer reduces the probability of a confident-but-wrong result.

Question / Input │ ┌───┴────────────────┐ ↓ ↓ ↓ Agent-A Agent-B Agent-C (independent, same prompt) │ │ │ ↓ ↓ ↓ Answer-A Answer-B Answer-C │ │ │ └───────────┴────────┘ │ Vote counter │ Majority / Weighted result

}}"""}]

async def consensus(
    question: str,
    options: list[str],
    n_agents: int = 5,
    models: list[str] | None = None
) -> dict:
    """
    Run N agents in parallel and aggregate votes.
    models: optional list to use different models (diversity increases value).
    """
    if not models:
        models = ["claude-sonnet-4-5"] * n_agents
    
    votes = await asyncio.gather(*[
        single_vote(f"agent-{i}", question, options, models[i % len(models)])
        for i in range(n_agents)
    ])
    
    # Tally votes with confidence weighting
    vote_counts = Counter(v["choice"] for v in votes)
    confidence_sums = {}
    for v in votes:
        confidence_sums[v["choice"]] = confidence_sums.get(v["choice"], 0) + v["confidence"]
    
    winner = max(vote_counts, key=lambda x: (vote_counts[x], confidence_sums.get(x, 0)))
    majority_votes = vote_counts[winner]
    agreement = majority_votes / n_agents
    
    return {
        "winner": winner,
        "agreement": agreement,  # 1.0 = unanimous
        "confident": agreement >= 0.6,
        "vote_breakdown": dict(vote_counts),
        "all_votes": votes
    }

# Diverse model consensus (best quality, higher cost)
async def diverse_consensus(question: str, options: list[str]) -> dict:
    return await consensus(
        question, options,
        n_agents=3,
        models=["claude-opus-4-5", "claude-sonnet-4-5", "claude-haiku-4-5"]
    )
When to use this

Classification decisions where error cost is high, security decisions (is this input safe?), code review verdicts (accept/reject PR), any binary or categorical decision where single-model confidence is insufficient.

Diversity increases value

Using different models (opus, sonnet, haiku) or different temperatures gets more genuine diversity than running the same model N times. Diverse model consensus with 3 agents often outperforms same-model consensus with 7.

Common mistakes
  • Using consensus for subjective questions. Consensus works for questions with a defensible correct answer. For "which writing style is better?" — it just measures which style the majority of models prefer, which may not match your users.
  • Ignoring low-agreement signals. If 3 of 5 agents agree but 2 dissent, that's a 60% agreement. Don't treat this like unanimous confidence — it signals genuine ambiguity.
  • Not logging dissenting votes. The minority view often contains the most important edge case reasoning. Always preserve the full vote record.

Exponential backoff with jitter

retry.pypython
import time
import random
import anthropic
from functools import wraps
from typing import TypeVar, Callable

T = TypeVar('T')

def with_retry(
    max_attempts: int = 4,
    base_delay: float = 1.0,
    max_delay: float = 60.0,
    retryable_status: tuple = (429, 529, 500, 503)
):
    """Decorator: exponential backoff with full jitter for API calls."""
    def decorator(fn: Callable[..., T]) -> Callable[..., T]:
        @wraps(fn)
        def wrapper(*args, **kwargs) -> T:
            last_error = None
            for attempt in range(max_attempts):
                try:
                    return fn(*args, **kwargs)
                except anthropic.RateLimitError as e:
                    last_error = e
                    if attempt == max_attempts - 1:
                        raise
                    # Full jitter: sleep uniform[0, min(cap, base * 2^attempt)]
                    cap = min(max_delay, base_delay * (2 ** attempt))
                    delay = random.uniform(0, cap)
                    time.sleep(delay)
                except anthropic.APIStatusError as e:
                    if e.status_code not in retryable_status:
                        raise
                    last_error = e
                    if attempt == max_attempts - 1:
                        raise
                    cap = min(max_delay, base_delay * (2 ** attempt))
                    delay = random.uniform(0, cap)
                    time.sleep(delay)
            raise last_error
        return wrapper
    return decorator

import json
import re

def extract_json(text: str, schema: dict | None = None) -> dict | None:
    """
    Robustly extract JSON from LLM output.
    Handles: JSON in code blocks, leading text, trailing text.
    """
    # Try code block first
    code_block = re.search(r'```(?:json)?\s*(\{.*?\})\s*```', text, re.DOTALL)
    if code_block:
        candidate = code_block.group(1)
    else:
        # Find outermost JSON object
        start = text.find('{')
        end = text.rfind('}')
        if start == -1 or end == -1:
            return None
        candidate = text[start:end+1]
    
    try:
        result = json.loads(candidate)
        # Validate required keys if schema provided
        if schema:
            required = schema.get("required", [])
            if not all(k in result for k in required):
                return None
        return result
    except json.JSONDecodeError:
        return None

from collections import deque
import hashlib

class LoopDetector:
    def __init__(self, window: int = 5, threshold: int = 2):
        self.history = deque(maxlen=window)
        self.threshold = threshold
    
    def check(self, action: str) -> bool:
        """Returns True if a loop is detected."""

        count = self.history.count(h)
        self.history.append(h)
        return count >= self.threshold

Context Window Management

Every agent has a finite context window. How you manage it determines whether long-running agents succeed or fail with a cryptic overflow error at step 47.

Context is currency

Every token in the context window costs money and competes for the model's attention. Large, unfocused context produces worse results than tight, relevant context. Treat context management as a first-class engineering concern.

Sliding window with summarization

import anthropic

client = anthropic.Anthropic()

class ContextManager:
    def __init__(self, max_tokens: int = 150_000, summary_trigger: float = 0.75):
        self.max_tokens = max_tokens
        self.summary_trigger = summary_trigger  # Summarize at 75% capacity
        self.messages: list[dict] = []
        self.summary: str = ""
        self._token_count = 0
    
    def add(self, role: str, content: str) -> None:
        self.messages.append({"role": role, "content": content})
        self._token_count += len(content) // 4  # Rough estimate
        
        if self._token_count > self.max_tokens * self.summary_trigger:
            self._summarize_and_compress()
    
    def _summarize_and_compress(self) -> None:
        """Summarize oldest half of conversation, keep recent messages."""
        keep_recent = len(self.messages) // 2
        to_summarize = self.messages[:-keep_recent]
        
        summary_prompt = """Summarize this conversation segment. Preserve:
- All decisions made
- All files/resources created or modified
- All errors encountered and their resolutions
- Current task state

Be concise. This summary replaces the raw conversation.

Conversation:
""" + "\n".join([f"{m['role']}: {m['content']}" for m in to_summarize])
        
        response = client.messages.create(
            model="claude-haiku-4-5",  # Cheap model for summarization
            max_tokens=1024,
            messages=[{"role": "user", "content": summary_prompt}]
        )
        
        new_summary = response.content[0].text
        self.summary = (self.summary + "\n" + new_summary).strip()
        self.messages = self.messages[-keep_recent:]
        self._token_count = sum(len(m["content"]) // 4 for m in self.messages)
    
    def get_messages(self, system_prompt: str = "") -> list[dict]:
        """Return messages with summary prepended if it exists."""
        if not self.summary:
            return self.messages
        
        summary_msg = {
            "role": "user",
            "content": f"[CONVERSATION SUMMARY]\n{self.summary}\n[END SUMMARY]\n\nContinuing from here:"
        }
        return [summary_msg] + self.messages

Cost Optimization

Agent costs compound. A task that costs $0.50 running once costs $50/day if scheduled hourly. Model selection, token budgets, and caching are the three levers that matter.

The cost equation

Total cost = (input tokens × input price) + (output tokens × output price) × number of agent calls.

In a multi-agent system, "number of agent calls" multiplies every inefficiency. An extra 500 tokens of context in a fan-out with 20 workers costs 10,000 tokens extra per run.

Token budget enforcementpython
from dataclasses import dataclass, field

@dataclass
class TokenBudget:
    total_limit: int = 500_000   # Per pipeline run
    per_call_limit: int = 8_192  # Max output per call
    used: int = 0
    calls: int = 0
    call_log: list = field(default_factory=list)
    
    def check(self, estimated_input: int) -> bool:
        """Returns False if budget would be exceeded."""
        return (self.used + estimated_input) < self.total_limit
    
    def record(self, stage: str, input_tokens: int, output_tokens: int) -> None:
        total = input_tokens + output_tokens
        self.used += total
        self.calls += 1
        self.call_log.append({"stage": stage, "tokens": total})
    
    @property
    def remaining(self) -> int:
        return self.total_limit - self.used
    
    @property
    def utilization(self) -> float:
        return self.used / self.total_limit

# Use in pipeline
budget = TokenBudget(total_limit=200_000)

def budgeted_call(prompt: str, stage: str, budget: TokenBudget) -> str | None:
    estimated = len(prompt) // 4
    if not budget.check(estimated):
        raise RuntimeError(f"Budget exhausted at stage '{stage}'. Used: {budget.used}/{budget.total_limit}")
    
    response = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=min(4096, budget.per_call_limit),
        messages=[{"role": "user", "content": prompt}]
    )
    usage = response.usage
    budget.record(stage, usage.input_tokens, usage.output_tokens)
    return response.content[0].text

Measure actual token usage on your first 10 runs before scheduling anything. Estimates are usually wrong by 2-3x. Set up budget alerts before you deploy to production.

Common mistakes
  • Using opus everywhere. Opus is 15x the cost of haiku. Audit every agent call and ask: does this specific step actually need opus-level reasoning?
  • Not using prompt caching. If your system prompt or skill files are >2048 tokens and used repeatedly, you're leaving significant money on the table.
  • No cost tracking in production. You will be surprised. Always log token usage per stage and aggregate it.

## Testing Protocol

Before shipping any agent change:
1. Run unit tests: `pytest tests/unit/ -v`
2. Run integration tests on 3 representative inputs
3. Check token usage didn't increase by more than 10%
4. Verify the agent exits cleanly (no infinite loops in test run)

- `tests/unit/` — pure function tests, no API calls, must be fast
- `tests/integration/` — marked @pytest.mark.integration, call real API

- Mock the API client for unit tests: `unittest.mock.patch('anthropic.Anthropic')`
- Never mock in integration tests — the point is to test real model behavior

  • Testing output text instead of structure. Exact text output from LLMs is non-deterministic. Test structure, schema compliance, and key facts — not exact strings.

agent_logger.pypython
import json
import time
import uuid
from datetime import datetime, timezone
from pathlib import Path
from dataclasses import dataclass, field, asdict

@dataclass
class AgentRun:
    run_id: str = field(default_factory=lambda: str(uuid.uuid4())[:8])
    agent: str = ""
    task: str = ""
    started_at: str = field(default_factory=lambda: datetime.now(timezone.utc).isoformat())
    finished_at: str = ""
    status: str = "running"  # running | success | failed
    stages: list = field(default_factory=list)
    total_tokens: int = 0
    total_cost_usd: float = 0.0
    errors: list = field(default_factory=list)

class AgentLogger:
    # Approximate pricing (USD per 1M tokens)
    PRICES = {
        "claude-haiku-4-5":   {"input": 0.25,   "output": 1.25},
        "claude-sonnet-4-5":  {"input": 3.00,   "output": 15.00},
        "claude-opus-4-5":    {"input": 15.00,  "output": 75.00},
    }
    
    def __init__(self, log_dir: str = "logs/agents"):
        self.log_dir = Path(log_dir)
        self.log_dir.mkdir(parents=True, exist_ok=True)
        self.run = None
        self._stage_start = None
    
    def start_run(self, agent: str, task: str) -> str:
        self.run = AgentRun(agent=agent, task=task[:200])
        return self.run.run_id
    
    def start_stage(self, name: str) -> None:
        self._stage_start = time.monotonic()
        self._current_stage = name
    
    def end_stage(self, model: str, input_tokens: int, output_tokens: int,
                   success: bool = True, error: str = None) -> None:
        duration = time.monotonic() - (self._stage_start or time.monotonic())
        prices = self.PRICES.get(model, {"input": 0, "output": 0})
        cost = (input_tokens * prices["input"] + output_tokens * prices["output"]) / 1_000_000
        
        stage_data = {
            "stage": self._current_stage,
            "model": model,
            "duration_s": round(duration, 2),
            "input_tokens": input_tokens,
            "output_tokens": output_tokens,
            "cost_usd": round(cost, 6),
            "success": success,
        }
        if error:
            stage_data["error"] = error
        
        self.run.stages.append(stage_data)
        self.run.total_tokens += input_tokens + output_tokens
        self.run.total_cost_usd += cost
    
    def end_run(self, status: str = "success") -> None:
        self.run.status = status
        self.run.finished_at = datetime.now(timezone.utc).isoformat()
        
        # Write to daily log file (JSONL format)
        log_file = self.log_dir / f"{datetime.now().strftime('%Y-%m-%d')}.jsonl"
        with open(log_file, "a") as f:
            f.write(json.dumps(asdict(self.run)) + "\n")
    
    def log_error(self, stage: str, error: str) -> None:
        self.run.errors.append({"stage": stage, "error": error,
                                  "timestamp": datetime.now(timezone.utc).isoformat()})

# Usage
logger = AgentLogger()
run_id = logger.start_run("code-reviewer", "Review PR #123")

logger.start_stage("analyze")
# ... call API ...
logger.end_stage("claude-sonnet-4-5", input_tokens=1200, output_tokens=450)

logger.end_run("success")

import os
import requests

def alert_on_failure(run_id: str, agent: str, error: str, stage: str) -> None:
    """Send alert when an agent run fails. Non-blocking."""
    try:
        bot_token = os.getenv("TELEGRAM_BOT_TOKEN")
        chat_id = os.getenv("TELEGRAM_CHAT_ID")
        
        if not (bot_token and chat_id):
            return
        
        msg = (f"🔴 Agent failure\n"
               f"Agent: {agent}\n"
               f"Run: {run_id}\n"
               f"Stage: {stage}\n"
               f"Error: {error[:200]}")
        
        requests.post(
            f"https://api.telegram.org/bot{bot_token}/sendMessage",
            json={"chat_id": chat_id, "text": msg},
            timeout=5
        )
    except Exception:
        pass  # Alerting must never crash the agent
Minimum viable observability

If you can only implement one thing: write JSONL logs with run_id, status, total_tokens, and error to a daily file. This gives you failure auditing and cost trending with minimal code.

Common mistakes
  • Logging only on failure. Log success runs too. You need the baseline to know when something degrades.
  • No run_id. Without a correlation ID, a log file full of errors tells you nothing about which run or pipeline stage they came from.
  • Alerting that blocks execution. Alerts must never crash agents. Wrap all alerting in try/except that swallows errors silently.

    response = await client.messages.create(
        model="claude-haiku-4-5",  # Cheap for individual topics
        max_tokens=2048,

Topic: {topic}

Include: key facts, current state, open questions, relevant context.
Be factual. Flag anything uncertain with "(uncertain)"."""}]
    )

async def research_synthesis(question: str, topics: list[str]) -> str:
    # Fan-out: research all topics in parallel
    semaphore = asyncio.Semaphore(5)
    async def bounded(t): 
        async with semaphore: return await research_topic(t)
    
    results = await asyncio.gather(*[bounded(t) for t in topics])
    
    # Fan-in: synthesize with better model
    sync_client = anthropic.Anthropic()
    research_text = "\n\n".join([f"## {r['topic']}\n{r['content']}" for r in results])
    
    response = sync_client.messages.create(
        model="claude-opus-4-5",
        max_tokens=8192,
        messages=[{"role": "user", "content": f"""Synthesize this research into a comprehensive answer.

Question: {question}

Research findings:
{research_text}

Write a structured report with: executive summary, key findings, analysis, open questions."""}]
    )
    return response.content[0].text

import anthropic
import json
from pathlib import Path

client = anthropic.Anthropic()

def transform_record(record: dict, schema: dict, transformation_rules: str) -> dict:
    """Use haiku to transform and validate a single record."""
    response = client.messages.create(
        model="claude-haiku-4-5",  # Critical: cheap model for volume
        max_tokens=512,
        messages=[{"role": "user", "content": f"""Transform this record according to rules.

Rules: {transformation_rules}

Record: {json.dumps(record)}

Output transformed record as JSON. If record is invalid, output:
{{"error": "reason", "original": record}}"""}]
    )
    
    text = response.content[0].text
    start, end = text.find('{'), text.rfind('}') + 1
    if start == -1:
        return {"error": "no JSON in response", "original": record}
    return json.loads(text[start:end])

def run_pipeline(records: list[dict], rules: str, output_path: str) -> dict:
    results = {"success": [], "failed": [], "total": len(records)}
    
    for i, record in enumerate(records):
        result = transform_record(record, {}, rules)
        if "error" in result:
            results["failed"].append({"index": i, **result})
        else:
            results["success"].append(result)
    
    # Write successful records
    Path(output_path).write_text(json.dumps(results["success"], indent=2))
    # Write failed records for review
    Path(output_path + ".failed.json").write_text(json.dumps(results["failed"], indent=2))
    return results
