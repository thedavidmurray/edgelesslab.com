28:T21db,<p>I maintain a small agent swarm that researches, drafts, codes, and reviews. Its model traffic passes through FreeLLMAPI, a local gateway that turns many provider credentials into one endpoint and model catalog.</p>
<p>For months it just worked. I remembered setting up somewhere between fourteen and seventeen providers, activating the premium gateway credential, and watching the swarm fall through free tiers when one provider was slow or exhausted. It became infrastructure in the most dangerous sense: reliable enough that I stopped thinking about how it worked.</p>
<p>Then I opened it and found four providers.</p>
<p>The FreeLLMAPI credential inside the tool was gone. Trying to activate it again returned a 400. The rest of my environment was intact, but the gateway had been hollowed out. Agents that depended on its catalog and fallback routes suddenly looked misconfigured.</p>
<h2 id="two-working-installations-made-one-broken-system">Two working installations made one broken system</h2>
<p>The failure was not a dramatic database crash. It was worse: a believable partial system.</p>
<p>FreeLLMAPI had been split between a Docker build and a native build. Each had its own database state. The native process was alive and serving requests, but it had the four-provider version. The older, richer state, including the active premium credential and the provider inventory I remembered, still existed on the Docker side. The activation request failed because I was asking one runtime to recognize state that belonged to the other.</p>
<p>Both installations were plausible. Together they had no source of truth. Depending on which database you inspected, FreeLLMAPI was licensed or unlicensed, rich in providers or reduced to four.</p>
<p>That is how configuration drift becomes an outage without anything technically going offline.</p>
<div class="blog-viz blog-flow"><div class="blog-viz-title">The split-state failure</div><div class="blog-flow-row"><span class="blog-flow-box">Native runtime</span><span class="blog-flow-arrow">→</span><span class="blog-flow-box">Four-provider state</span><span class="blog-flow-arrow">→</span><span class="blog-flow-box">Activation fails</span></div><div class="blog-flow-row"><span class="blog-flow-box">Docker runtime</span><span class="blog-flow-arrow">→</span><span class="blog-flow-box">Older rich state</span><span class="blog-flow-arrow">→</span><span class="blog-flow-box">Premium active</span></div></div>
<h2 id="recover-the-state-before-redesigning-the-system">Recover the state before redesigning the system</h2>
<p>The tempting response was to re-enter keys from environment files and rebuild the provider list by hand. That would have produced a third interpretation of the setup. Instead I treated the databases as recovery evidence.</p>
<p>I compared the databases, checked their integrity, counted credentials without printing them, and reconciled the provider rows against the current build. The recovered state held <strong>21 credential rows across 19 providers</strong>, with twenty enabled. Nineteen enabled credentials passed health checks. The premium license was still active. The setup had not disappeared; I had been looking at the wrong state store.</p>
<div class="blog-viz blog-metrics"><div class="blog-metric"><div class="blog-metric-value">4</div><div class="blog-metric-label">Providers in the partial state</div></div><div class="blog-metric"><div class="blog-metric-value">19</div><div class="blog-metric-label">Providers recovered</div></div><div class="blog-metric"><div class="blog-metric-value">21</div><div class="blog-metric-label">Credential rows reconciled</div></div><div class="blog-metric"><div class="blog-metric-value">19</div><div class="blog-metric-label">Enabled credentials healthy</div></div></div>
<p>Only after recovery did I choose a permanent owner. A native service now owns the verified database, binds only to the local machine, restarts automatically, and writes encrypted hourly backups. Docker was retired from production.</p>
<p>One service. One database. One recovery path.</p>
<h2 id="the-curation-that-did-more-than-the-budget">The curation that did more than the budget</h2>
<p>Before consolidation, some agents used bare <code>auto</code> routing: whatever the gateway happened to prefer. There was no intentional curation or guard against an expensive model being selected automatically.</p>
<p>The fix was creating three named route selectors:</p>
<ul><li><strong><code>auto:smart-core</code>:</strong> the strongest automatically routed free model pool. Every route in it had passed a live completion canary. No assumptions, no untested providers.</li><li><strong><code>auto:fast-core</code>:</strong> a speed-optimized pool for routine work. Models are sorted by intelligence within the fast tier, so the best quick model wins.</li><li><strong><code>fusion:smart-core</code>:</strong> a synthesis route for editorial review. Its judge is pinned to one model, and the most expensive free model is explicitly excluded from the automatic pool.</li></ul>
<p>The key rule: Hyper DeepSeek V4 Pro and any paid Nous model are <strong>manual escalation only</strong>. They never appear in a primary route, a fallback chain, a Fusion panel, or an automatic judge. I can still use them when a task genuinely needs the extra capability, but it has to be a deliberate choice, not a silent default.</p>

<h2 id="the-same-agents-suddenly-smarter">The same agents, suddenly smarter</h2>
<p>Once the routes were named and curated, I assigned them:</p>
<ul><li><strong>Atlas</strong>, <strong>Hive</strong>, and <strong>Beau</strong>, the research and dispatch agents, got Hyper DeepSeek V4 Flash as their primary, with <code>auto:smart-core</code> and NVIDIA GPT-OSS as fallbacks.</li><li><strong>Builder</strong>, the implementation agent, uses a free MOA blend that composites multiple free models, with <code>auto:fast-core</code> and V4 Flash as fallbacks.</li><li><strong>Honey</strong>, the editorial agent, uses V4 Flash with Fusion as its review/fallback layer.</li></ul>
<p>The smartest discovery: Hive is the <strong>sole continuous dispatcher</strong> for the swarm's task board. Atlas is the standby if Hive is taken offline. One agent polls, the rest do one-shot work. This rule alone eliminated the most common failure mode in a multi-agent system: competing dispatchers stepping on each other.</p>
<h2 id="the-lesson-worth-stealing">The lesson worth stealing</h2>
<p>I thought the swarm needed a paid model budget. It needed a receipt audit: find what I already had, verify it, and route it intentionally.</p>
<ul><li><strong>Inventory before you buy.</strong> The credential you already have, tested and routed, beats the one you're about to sign up for. I had 19 healthy credentials and didn't know it.</li><li><strong>A named selector beats bare auto.</strong> <code>auto:smart-core</code> preserves intent even if the dashboard's active profile changes. Bare <code>auto</code> is a gamble on whatever the gateway happens to prefer today.</li><li><strong>Exclude the expensive ones on purpose.</strong> If a paid model isn't your primary, it shouldn't be in your automatic fallback either.
